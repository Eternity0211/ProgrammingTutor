# ProgrammingTutor 全套收益评估报告（A/B/C，D 暂缓）

## 1. 对比口径

- **A**：`688863a`，当前功能分支开始前的基线。
- **B**：`9b009bb`，包含原有功能改造、但不包含本轮 P0-P3 收尾的版本。
- **C**：当前 `feature-agent-tutor`，包含本轮 P0-P3 改造及 DeepSeek-only 关键词 RAG。
- **D**：并行 Agent 版本，按要求本轮不测试。
- A/B/C 使用同一批 3 个合成 C++ 场景、同一 DeepSeek 配置，并各运行 2 轮；因此时间结果只能作为受控样本，不等同于生产压测。

## 2. 多轮端到端 Agent 对比

每个场景依次运行 Code Review、Emotion、Navigation，记录串行关键路径。

| 版本 | 场景样本数 | 平均耗时/场景 | P50 | P95 | 最小-最大 |
|---|---:|---:|---:|---:|---:|
| A | 6 | 23.40s | 22.68s | 25.88s | 18.31-28.21s |
| B | 6 | 21.77s | 20.79s | 22.16s | 18.62-26.50s |
| C | 6 | 22.86s | 20.48s | 26.57s | 19.40-27.73s |

两轮总耗时均值：A **70.20s**、B **65.30s**、C **68.59s**。在这个小样本中，C 相对 A 约快 **2.3%**，但 P95 比 A 高约 **2.7%**；这说明当前串行结构的端到端提速不稳定，网络和模型响应抖动大于代码本身的差异，不能宣称已有显著性能收益。B 比 A 快约 **7.0%**，C 比 B 慢约 **5.0%**，主要反映提示词、输出内容和模型调用路径变化，而不是功能退化。

质量抽查中，三个版本都能识别“运算符优先级”和“内存泄漏”场景，并对干净循环给出无严重问题的结论。当前脚本记录了各 Agent 是否有结构化结果；由于 Emotion 的默认降级结果与“平静/代码执行顺利”的正常结果字段相同，不能仅靠结果 JSON 可靠区分一次真实降级，后续应在运行元数据中增加 `fallbackUsed`。

原始数据：`benefit-A.json`、`benefit-B.json`、`benefit-C.json` 及对应的 `*-r2.json`。

## 4. 真实外部服务检查

已执行真实集成开关：

- PostgreSQL：真实连接和查询通过。
- Neo4j：失败，`No routing servers available` / `ECONNREFUSED ::1:7687`，说明本机 Neo4j 未监听或 Docker Engine 当前不可用。
- Judge0：失败，配置的服务地址 `fetch failed`，说明 Judge0 服务不可达。

因此 Neo4j/Judge0 的失败属于本地外部依赖未启动/不可达，不能据此判定应用代码失败；要完成真实服务收益测试，需要先启动对应服务，再重复同一命令。

## 6. 结论

P0-P3 的代码链路和本地自动化质量检查已覆盖并通过；本轮没有证据表明串行 Agent 已获得稳定的端到端性能提升。收益目前更明确地体现在可观测性、降级能力、RAG 可运行、数据集校验和跨模块测试覆盖，而不是秒级提速。要量化“提效多少”和“解决多少问题”，下一步应优先：

1. 给每次 Agent 调用记录统一的 token、耗时、fallback、错误和 trace id；
2. 启动 Neo4j/Judge0 后完成真实服务复测；
3. 建立带参考答案和修复标签的评测集，统计 Review 准确率、修复成功率、导航命中率和 Emotion 一致性；
4. 再实现 D 并行版本，并用完全相同的场景和指标与 C 对比。
